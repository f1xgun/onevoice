# NATS transport security

The internal A2A bus (orchestrator/api → platform agents) runs on NATS. Auth is
**per-service nkey** with **subject-scoped permissions**, over **mandatory TLS**.
There is no shared password: a compromised container can only use the subjects
its own identity is allowed to, which contains cross-tenant publish, `tool_result`
spoofing, and HITL-bypass to the blast radius of a single service.

## How it works

- Each service has its own ed25519 **nkey** user seed (`infra/nats/creds/<service>.nk`).
  The seed signs the server's connection nonce; it never crosses the wire. Clients
  load it via `NATS_NKEY_SEED` (see `pkg/natsauth`).
- The server (`nats-server.conf`) `include`s `creds/auth.conf` — a generated
  `authorization { users: [...] }` block mapping each service's **public** key to a
  publish/subscribe allow-list. Only public keys live in that file.
- **TLS** is mandatory: the server presents `nats.crt` (SAN `DNS:nats`) and every
  client verifies it against the shared dev CA (`NATS_CA_PATH`). Client identity is
  the nkey, so no client certificate is required.

## Provisioning (before `docker compose up`)

```bash
make nats-creds   # per-service nkey seeds + auth.conf → infra/nats/creds/
make mtls-certs   # dev CA + nats server cert (+ HTTP mTLS leafs) → infra/mtls/certs/
```

Both are idempotent and write only to gitignored directories (a `.gitignore` stub
keeps the dir tracked). To rotate: `make clean-nats-creds && make nats-creds`
(then restart the stack so every service reloads its seed).

**Dev only.** These scripts mint a local CA and seeds for `docker compose`.
Production must provision its own CA and seeds out of band and mount them at the
same paths; never ship the dev material. (Same rule as `infra/mtls/README.md`.)

## Permission model

Generated by `tools/natskeygen` from the verified per-service pub/sub map. The
generator's `perms` table is the source of truth; keep it in sync with
`pkg/a2a/protocol.go` subjects.

| Service | publish | subscribe | replies |
|---|---|---|---|
| orchestrator | `tasks.*` | `_INBOX.>` | — |
| api | `tasks.*`, `integrations.revoked.*.*` | `_INBOX.>`, `hitl.callbacks.telegram`, `hitl.owner_link.telegram` | — |
| agent-telegram | `hitl.callbacks.telegram`, `hitl.owner_link.telegram` | `tasks.telegram`, `integrations.revoked.telegram.*` | `allow_responses` |
| agent-vk | — | `tasks.vk`, `integrations.revoked.vk.*` | `allow_responses` |
| agent-yandex-business | — | `tasks.yandex_business`, `integrations.revoked.yandex_business.*` | `allow_responses` |
| agent-google-business | — | `tasks.google_business`, `integrations.revoked.google_business.*` | `allow_responses` |

`allow_responses` lets an agent reply only to the inbox of a request it actually
received — it never grants blanket `_INBOX.>` publish. Requesters (orchestrator,
api) originate `tasks.*` and read their own reply inboxes; no service can
subscribe another agent's `tasks.<platform>` subject or publish a task it isn't
entitled to.

## Linux credential ownership

The Yandex agent runs as `pwuser` (UID/GID 1000) with all capabilities dropped.
Linux bind mounts preserve host ownership; root-generated 0600 files are not
readable by that agent. Keep seeds private (0600), and assign **only its own**
seed to its runtime identity before deployment, and after credential rotation:

```bash
sudo chown 1000:1000 infra/nats/creds/agent-yandex-business.nk
sudo chmod 600 infra/nats/creds/agent-yandex-business.nk
```

The seed is mounted as a single file. For mTLS directory traversal and its leaf
key ownership, also follow [the mTLS instructions](../mtls/README.md#linux-credential-ownership).
Do not recursively assign all credentials to the browser worker. Missing,
unreadable or malformed seeds now fail connection setup with the file path.

## Updating reply permissions without rotating identities

Agent replies are limited to one response within five minutes. The orchestrator
rejects `TOOL_EXEC_TIMEOUT` above 4m30s, reserving 30s for delivery. Existing
`auth.conf` files are gitignored and ordinary generation skips them. Refresh
permissions from the existing seeds when deploying this change:

```bash
go run ./tools/natskeygen -refresh
```

This updates only `auth.conf`; it never rotates seeds. Deploy the refreshed
configuration and reload NATS through your normal maintenance procedure. A code
update alone does not change permissions on a running broker.
