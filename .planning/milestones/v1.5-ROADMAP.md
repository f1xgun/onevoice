# Roadmap: v1.5 Paid MVP

**Status:** 📋 Planned
**Source:** Synthesized from 5-agent audit (2026-05-24) — see `LAUNCH-AUDIT-2026-05-24.md`
**Target duration:** 3–4 weeks
**Prerequisite:** v1.4 Launch Readiness must ship first — billing requires the `BusinessID`-keyed cost trail from Phase 25.

## Milestone Goal

Take real money from real Russian businesses with proper per-tenant accounting, 54-ФЗ-compliant fiscal receipts, and a single working subscription tier — without locking ourselves out of multi-tier expansion later.

## Definition of Done

1. A business owner can pick a plan on the pricing page → pay via YooKassa → receive a 54-ФЗ fiscal receipt by email → see "Plan: Pro" reflected in `/settings/billing` → make a successful chat call that decrements the plan's daily allowance.
2. When a subscription lapses, the business is soft-blocked (banner + degrade to 1 LLM call/day, no hard delete).
3. Webhook idempotency prevents double-charge on YooKassa retries.
4. Operator can pull a revenue report and an OpenRouter-cost report per business for any month.

## Out of Scope (deferred to v1.6+)

- Multiple payment providers (CloudPayments, SBP as second rail) — v1.6
- Closing documents (акты/УПД via Diadoc/Kontur) for B2B — v1.6
- Self-serve cancel flow → v1.6 (manual cancel via support email is acceptable for MVP)
- Trial period mechanics — v1.6
- Dunning emails — v1.6
- Tier ladder (Free / Pro / Enterprise) — v1.5 ships single Pro tier; ladder is v1.6

## Phases

### Phase 27: Billing Schema & B2B Requisites
**Goal:** Data model is correctly shaped to invoice a Russian legal entity per-business.
**Depends on:** Phase 25 (usage_logs already has `business_id`)
**Severity:** P0 (gates all subsequent phases)
**Success Criteria:**
1. `businesses` table adds columns: `plan TEXT NOT NULL DEFAULT 'free'`, `legal_name TEXT`, `inn TEXT`, `kpp TEXT`, `legal_address TEXT`, `is_legal_entity BOOLEAN DEFAULT false`. Migration in both `migrations/postgres/` and `services/api/migrations/`.
3. `subscriptions` table (already exists per `migrations/postgres/000001_init.up.sql:64-74`) rekeyed from `user_id` to `business_id`; columns: `id`, `business_id`, `plan`, `status` (active/grace/expired/cancelled), `current_period_start`, `current_period_end`, `cancel_at_period_end`, `external_provider`, `external_subscription_id`.
4. `plan_definitions` table seeded with `free` and `pro` rows: monthly price RUB, daily LLM USD cap, max integrations, max members, feature flags JSON.
5. `BusinessPlanResolver` service: `(business_id) → PlanDefinition` with 60s cache; replaces the hardcoded env `LLM_TIER` fallback in `services/api/internal/config/config.go:245-247` and `services/orchestrator/internal/config/config.go:82`.
6. `/api/v1/businesses/{id}/requisites` endpoint to read/update legal-entity fields; `members.update` permission gates write.
**Expected plans:** 3
**UI hint:** yes (requisites form)

### Phase 28: YooKassa Integration
**Goal:** Money flows from customer to operator account; receipts issued.
**Depends on:** Phase 27
**Severity:** P0
**Success Criteria:**
1. `POST /api/v1/billing/checkout` creates a YooKassa payment for `(business_id, plan)`, returns `confirmation_url` for redirect. Request body includes `receipt` block (`items`, `customer.email`, `tax_system_code`) so YooKassa auto-issues the 54-ФЗ fiscal receipt.
2. `POST /api/v1/payments/yookassa/webhook` verifies HMAC signature, deduplicates by `payment_id` (PG unique constraint on `external_event_id`), and dispatches to a typed handler per `event` (`payment.succeeded`, `payment.canceled`, `refund.succeeded`).
3. Idempotency key on YooKassa side: `business_id + plan + period_start` so retried checkout requests don't double-charge.
4. `payment_events` audit table: every webhook stored raw with `processed_at`, `result`, `error`.
5. Webhook handler rate-limited (`/payments/yookassa/webhook` 100/min/IP) and IP-allowlisted to YooKassa's published ranges.
6. Sandbox-mode flag in env so we can E2E-test against YooKassa sandbox before flipping to prod.
**Expected plans:** 3
**UI hint:** no (operator + redirect URL only)

### Phase 29: Subscription Lifecycle
**Goal:** Plan state stays correct as payments succeed, lapse, or refund.
**Depends on:** Phase 28
**Severity:** P0
**Success Criteria:**
1. `payment.succeeded` upserts `subscriptions` row: `status=active`, `current_period_end = now + 1 month`. `businesses.plan = 'pro'`.
2. Daily cron `subscription_lapse_sweeper` flags `current_period_end < now` as `status=grace` (3-day grace), then `status=expired` (back to plan `free` with banner).
3. `payment.canceled` and `refund.succeeded` paths transition subscription to `cancelled` and `refunded` respectively.
4. `BillingMiddleware` checks plan/subscription on every chat request: if `expired` and `daily_spend > free_cap`, return `402 Payment Required` with a structured error code that the frontend renders as upgrade-CTA.
5. Audit log entries for every subscription transition (`audit.actions.go` extended).
6. Operator endpoint `GET /admin/subscriptions?status=lapsed` for support triage.
**Expected plans:** 3
**UI hint:** banner only

### Phase 30: Billing Frontend
**Goal:** Self-serve "see my plan, see my usage, upgrade" flow.
**Depends on:** Phase 27, Phase 28
**Severity:** P0
**Success Criteria:**
1. Re-enable pricing section in `services/frontend/app/page.tsx:495-554` (currently commented out per project memory); update copy to match `plan_definitions`.
2. `/settings/billing` page: current plan card, usage chart (this month's LLM spend per business by day from `usage_logs`), invoices list (link to receipt URLs from YooKassa), "Upgrade / Change plan" button → checkout redirect.
3. `/settings/billing/requisites` form: ИНН, КПП, юр. адрес, юр. наименование. Validated client + server.
4. Upgrade-CTA banner appears in chat + dashboard when `subscription.status in ('grace', 'expired')`.
5. Russian-only copy (with `en.json` parity at translation level — actual market is Russian).
**Expected plans:** 3
**UI hint:** yes

### Phase 31: Production Load Hardening
**Goal:** First 100 concurrent paying customers don't tip the system over.
**Depends on:** Nothing critical (parallel-safe with Phase 27–30 if capacity permits)
**Severity:** P1
**Success Criteria:**
1. k6 load script in `test/load/` covering: 50 concurrent chat-with-tool-call sessions for 10 minutes; report p50/p95/p99 SSE TTFB, error rate, OpenRouter spend.
2. Add `Retry-After`-aware exponential backoff in `pkg/llm/providers/openai.go` and `pkg/llm/providers/anthropic.go` for upstream 429.
3. Surface `429 retry-after` SSE event to frontend with countdown UX ("LLM temporarily rate-limited, retrying in 5s…").
4. Postgres `application_name` set per service in pgxpool config for `pg_stat_activity` visibility.
5. Documented capacity baseline: "1 vCPU + 2 GB RAM serves up to N concurrent businesses based on the k6 run."
**Expected plans:** 3
**UI hint:** chat banner only

## Risks

| Risk | Mitigation |
|------|-----------|
| YooKassa sandbox parity with prod (some edge cases only show in prod) | Run 2 weeks of zero-cost "real" checkouts (1 ₽ test plans) before public launch |
| Reseating `subscriptions` PK from `user_id` to `business_id` if dev data exists | Migration writes a fresh table; old empty `subscriptions` truncated; documented in migration comment |
| 54-ФЗ receipt format errors → YooKassa rejects payment creation | Use YooKassa's tested receipt builder; lock VAT and tax_system_code in env (defaults to "1" — упрощёнка) |
| Single-provider lock-in (YooKassa only) | Webhook handler abstracted behind `PaymentProvider` interface so CloudPayments can be added in v1.6 without rewrite |
| Operator-side fiscalization compliance (касса) | YooKassa acts as fiscal agent — no own касса needed; document this in `docs/billing.md` |
