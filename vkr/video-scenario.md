# Сценарий видеоролика для защиты ВКР (3 мин)

## Легенда

**Кофейня "Кофе & Булка"** --- небольшой бизнес с присутствием на трёх площадках: группа ВКонтакте, Telegram-канал и карточка в Яндекс.Бизнесе. Владелица Анна ведёт всё сама.

**Проблема:** На прошлой неделе Анна поменяла график в Яндекс.Бизнесе, но забыла обновить его в VK --- клиент пришёл к закрытой двери. Негативный отзыв на картах висел без ответа три дня. Чтобы выложить один и тот же пост, нужно заходить на три платформы.

---

## Блок 1. Вступление --- постановка проблемы [0:00 -- 0:25]

**Экран:** слайд с проблемой или схема AS-IS.

**Закадровый текст:**

> Допустим, у нас есть кофейня, и она есть на трёх площадках: VK, Telegram и Яндекс.Бизнес. Владелец обновляет всё вручную --- заходит на каждую платформу, проверяет отзывы, публикует посты. Если меняется график работы --- легко забыть обновить одну из площадок, и клиент приходит к закрытой двери. Отзывы копятся без ответа, данные расходятся. Моя система OneVoice позволяет управлять всеми площадками из одного интерфейса: писать посты, отвечать на отзывы, обновлять информацию --- всё через один чат.

---

## Блок 2. Владелец: настройка системы [0:25 -- 1:00]

**Роль:** Анна (owner --- полный доступ)
**Экран:** скринкаст реальной работы системы.

### Шаг 1. Регистрация и вход
- Экран регистрации: имя, email, пароль.
- Вход в систему.

### Шаг 2. Создание профиля бизнеса
- Раздел **"Бизнес"**.
- Заполняем данные: название "Кофе & Булка", категория "Кафе / Ресторан", адрес, телефон, сайт, описание.
- Настройка расписания (понедельник--воскресенье, 08:00--22:00).

### Шаг 3. Подключение интеграций
- Раздел **"Интеграции"**.
- Подключаем **Telegram** (вводим токен бота).
- Подключаем **ВКонтакте** (OAuth-авторизация).
- Подключаем **Яндекс.Бизнес** (учётные данные для RPA).
- В сайдбаре видны три платформы со статусом "Подключено".

**Закадровый текст:**

> Анна заполняет данные бизнеса в одном месте и подключает площадки. Telegram и VK подключаются через официальные API. А вот у Яндекс.Бизнеса публичного API нет, поэтому для него используется браузерная автоматизация --- RPA на базе Playwright. Для пользователя разницы нет, всё выглядит одинаково.

---

## Блок 3. Обновление информации на всех площадках через AI-чат [1:00 -- 1:45]

**Роль:** Анна (owner)
**Экран:** раздел "Чат" --- создание нового диалога.

### Демонстрация

1. Анна нажимает **"+ Новый диалог"**.
2. Пишет в чат: **"Обнови описание кофейни на всех площадках: добавь, что у нас открылась летняя веранда"**.
3. Оркестратор разбирает запрос и вызывает нужные инструменты:
   - `vk__update_group_info` --- обновление описания группы VK через API.
   - `yandex_business__update_info` --- обновление карточки через Playwright.
4. На экране в реальном времени видно (SSE-стриминг):
   - Какой инструмент вызван и с какими параметрами.
   - Статус выполнения.
   - Результат.
   - Итоговый ответ.
5. В разделе **"Задачи"** --- выполненные задачи с платформой, типом и статусом "Завершено".

**Закадровый текст:**

> Одна команда в чате --- и описание обновилось на всех площадках. Оркестратор на базе LLM сам понимает, какие агенты нужны: для VK вызывается API-агент, для Яндекс.Бизнеса --- RPA-агент. Пользователь просто пишет текстом и не думает, как именно система взаимодействует с каждой платформой. Весь процесс транслируется через Server-Sent Events.

---

## Блок 4. Сбор и обработка отзывов [1:45 -- 2:20]

**Роль:** Анна (owner)
**Экран:** чат с AI-ассистентом, затем раздел "Отзывы".

### Демонстрация

1. В чате Анна пишет: **"Собери новые отзывы с Яндекс.Бизнеса"**.
2. Оркестратор вызывает `yandex_business__get_reviews` --- RPA-агент через Playwright открывает страницу организации и собирает отзывы.
3. AI возвращает сводку: **"Найдено 3 новых отзыва: 2 положительных, 1 негативный о долгом ожидании"**.
4. В разделе **"Отзывы"** --- отзывы с фильтрацией по платформе и статусу (все / без ответа / с ответом).

**Закадровый текст:**

> Все отзывы --- в одном окне. RPA-агент заходит на Яндекс.Бизнес через браузер и собирает отзывы, как это сделал бы человек. Чтобы не выглядеть как бот, между действиями добавляются случайные задержки, а перед каждой операцией проверяется, что сессия ещё валидна.

---

## Блок 5. Публикация поста через чат [2:20 -- 2:45]

**Роль:** Анна (owner)
**Экран:** чат -> раздел "Посты".

### Демонстрация

1. В чате Анна пишет: **"Опубликуй в Telegram-канале пост: Открытие летней веранды! Ждём вас с 10:00"**.
2. Оркестратор вызывает `telegram__send_channel_post` --- агент отправляет пост через Telegram Bot API.
3. AI подтверждает: **"Пост опубликован в Telegram-канале"**.
4. В разделе **"Посты"** --- запись со статусом "Опубликован", платформа Telegram, дата.

**Закадровый текст:**

> Публикация --- тоже через чат. Telegram-агент работает через Bot API, поддерживает текст и картинки. VK-агент, кроме обычных постов, умеет ещё и отложенные --- можно запланировать публикацию на нужное время.

---

## Блок 6. Заключение [2:45 -- 3:00]

**Экран:** схема TO-BE или итоговый слайд.

**Закадровый текст:**

> Итого: OneVoice позволяет малому бизнесу управлять всеми площадками из одного места. За счёт мультиагентной архитектуры система работает и с платформами, у которых есть API, и с теми, где API нет --- через браузерную автоматизацию. Вместо того чтобы заходить на три сайта, владелец пишет одну команду в чате.

# Техническая реализация: что происходит под капотом

## Архитектура

Система состоит из 6 микросервисов и общей библиотеки:

```
Frontend (Next.js) --REST/SSE--> API (Go) --HTTP--> Orchestrator (Go)
                                                        |
                                                   NATS (брокер)
                                                   /    |    \
                                           Telegram  VK   Yandex.Business
                                           (API)    (API)  (RPA/Playwright)
```

## Поток обработки запроса в чате

```
1. Пользователь пишет сообщение в чат (Next.js)
2. Frontend отправляет POST /api/v1/conversations/{id}/chat
3. API-сервис добавляет контекст бизнеса:
   - профиль (название, адрес, телефон, описание)
   - список подключённых интеграций
   - историю диалога
4. API проксирует запрос к Orchestrator (POST /chat/{id})
5. Оркестратор:
   a. Формирует системный промпт с контекстом бизнеса
   b. Фильтрует инструменты по подключённым интеграциям
   c. Отправляет запрос к LLM (OpenAI/Anthropic/OpenRouter)
   d. LLM возвращает tool_call (например, telegram__send_channel_post)
   e. По префиксу имени определяется агент: telegram__ -> tasks.telegram
   f. NATS request на subject tasks.telegram
   g. Telegram-агент получает задачу, выполняет через Bot API
   h. Результат возвращается через NATS reply
   i. Оркестратор передаёт результат обратно в LLM
   j. LLM формирует ответ (или вызывает следующий инструмент)
   k. Цикл повторяется (макс. 10 итераций)
6. Все события стримятся через SSE: text, tool_call, tool_result, done
7. Frontend отображает каждое событие в реальном времени
```

## Протоколы

| Протокол | Направление | Зачем |
|----------|-------------|-------|
| REST (HTTP/JSON) | Frontend <-> API | CRUD, аутентификация |
| SSE | API -> Frontend | Стриминг ответов LLM и статусов инструментов |
| NATS (Request/Reply) | Orchestrator <-> Agents | Отправка задач агентам |

## Типы агентов

### API-агенты (VK, Telegram)
- Работают через официальные API платформ.
- Используют OAuth-токены / Bot-токены.
- Быстрое выполнение (миллисекунды).

### RPA-агент (Яндекс.Бизнес)
- Работает через браузерную автоматизацию Playwright (headless Chromium).
- Эмулирует действия человека в веб-интерфейсе.
- Случайные задержки 1--4 сек между действиями, чтобы не выглядеть как бот.
- Перед каждой операцией проверяет, что сессия валидна (canary check).
- При ошибке делает скриншот для диагностики.
- Работает медленнее (секунды), но зато покрывает платформы без API.

## Главное архитектурное решение

Все агенты работают по одному протоколу. Оркестратор отправляет стандартное сообщение через NATS и не знает, как именно агент выполняет задачу --- через REST API или через браузер. Благодаря этому, чтобы добавить новую платформу, достаточно написать нового агента, подписать его на NATS-subject и зарегистрировать инструменты. Ядро системы менять не нужно.
